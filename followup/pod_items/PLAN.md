## Item A: SGLang `main` build and environment (for 3b; written 2026-11-24 about 08:00 UTC local, before running)

- Purpose: 3b compares SGLang v0.5.23 with `main`, which has PR #46500 (the drainer). The environment must exist before the dedicated session so that session spends no time building.
- Commit: `main` of `sgl-project/sglang` at the time of the build; the SHA is read with `git ls-remote` immediately before and recorded in the setup log (at 06:46 UTC on 2026-11-24 it was `0e9cff98f5b7`). If `main` moves during the build, the recorded commit is the one actually checked out, never "latest".
- Method: clone that commit into `/workspace/src/sglang-main`; copy the v0.5.23 environment as hard links (`cp -al /workspace/envs/sglang /workspace/envs/sglang_main`) so almost no disk is used (the disk has about 16 GB free and the environment is 11 GB); install the checkout into the copy with `uv pip install` (this replaces files by new ones and leaves the original environment intact; its integrity is checked by importing `sglang` from it afterwards and comparing `uv pip list`). The package versions that change are recorded as a diff of `uv pip list` between the two environments.
- Check (no latency): import of `sglang` from the new environment reports the checked-out commit's version string; a server start with the study's LoRA flags reaches ready on the 32 adapters at scale 0.05 and is stopped (this uses the GPU for about two minutes, startup log kept). Whether `--lora-drain-wait-threshold` exists in this build is read from `--help` and recorded; PR #46500's presence is confirmed by `git log` for its merge commit.
- Not done here: no benchmark, and no decision about what counts as "improved" (that is in the dedicated-session plan).
- If the install fails or breaks the environment, the failure is logged in `docs/BUGS.md` with the error text, upstream issues are searched, and the item stops.

## Item B: slot memory and KV capacity at 16, 32 and 64 slots, from startup logs (the memory part of 3c; written 2026-11-24 about 08:00 UTC local, before running)

- Purpose: how GPU memory and KV-cache capacity change with the number of LoRA slots, for vLLM 0.34.0 and SGLang 0.5.23. No request is sent; no latency or throughput is measured.
- Configurations, one server start each: slots 16, 32, 64 with the 32 study adapters (scale 0.05, seeds 0 to 31, checksums equal the study's manifest), and slots 64 with 128 adapters (scale 0.05, seeds 0 to 127, generated by `scripts/make_adapters.py`, checksums compared with the study's manifest, which lists 128). Flags as in the study: vLLM `--max-model-len 4096 --gpu-memory-utilization 0.85 --enable-lora --max-loras N --max-cpu-loras 128 --max-lora-rank 16`; SGLang `--mem-fraction-static 0.85 --context-length 4096 --enable-lora --max-lora-rank 16 --max-loras-per-batch N` with the seven target modules; all adapters named in `--lora-modules` or `--lora-paths`. Prefix caching and the radix cache are left at their defaults (on), as in the main grid.
- Recorded per start: the KV-cache size line of the log (tokens, and GiB where the log gives it), the LoRA memory pool line if present, `nvidia-smi` memory used once the server reports ready and the GPU is idle, whether startup succeeded, and any error text (an out-of-memory failure is a result, not a retry trigger; each configuration is run once, and repeated once more only if the first start failed for a reason that is not memory, with both attempts reported).
- Reading: tabulate slots against KV tokens and GPU memory per engine; state the change from 16 to 32 to 64 and what fraction of the 24 GB card the LoRA pool takes. This is a read from logs of one start per configuration; no variance is estimated.
- One server at a time; GPU idle before each start (checked, not a quiet-window check). Load and external CPU are logged for information only.

## Item C: B8 minimal reproduction on SGLang `main` and a regression test (3d; written 2026-11-24 about 08:20 UTC local, before running)

Reason it runs: 2d found by reading that `main` (`0e9cff98f5b7`, checked out for Item A) still applies the model's generation_config on chat only. The author asked for a reproduction on `main` and a regression test that fails before any fix. No fix is written (the author wants to see the issue reply first), and nothing is posted.
- Reproduction (GPU, correctness only, no timing): SGLang `main` server (environment of Item A), `Qwen2.5-1.5B-Instruct`, no LoRA, default flags (`--sampling-defaults` left at its default), `--context-length 8192`. For 64 fixed prompts (the differential study's prompt set), two requests per endpoint with `temperature: 0`, `max_tokens` 128, served one at a time: (i) only `temperature: 0`; (ii) `temperature: 0` plus the model's own generation_config values (`repetition_penalty` 1.1, `top_p` 0.8, `top_k` 20). If the server applies the model defaults on an endpoint, (i) and (ii) are identical on it, apart from nondeterminism that a repeat of (i) measures. Endpoints: `/v1/chat/completions`, `/v1/completions`, `/generate`. Result per endpoint: number of prompts (of 64) where (i) differs from (ii), and where (i) differs from a repeat of (i). Reading, fixed now: the defaults count as applied on an endpoint if the (i)-vs-(ii) difference count is at most the (i)-vs-repeat count; as not applied if it is larger by 8 or more of 64; anything between is reported as unclear. The server log line about default chat sampling params is also recorded.
- Test (no GPU): `followup/sglang_issues/test_completions_sampling_defaults.py` builds the completions request handler of `main` with a stub tokenizer manager whose model config returns the model's defaults, builds the sampling parameters for a request that sets only `temperature`, and asserts that `repetition_penalty`, `top_p` and `top_k` come from the model. A second case asserts a request-supplied `top_p` wins; a third that the schema defaults hold when `--sampling-defaults openai`. It is run on `main` unchanged to show it fails (first case) and passes (second and third), with the pytest output saved. If the handler cannot be built without a model, the test falls back to calling its sampling-parameter function directly and says so.

## Item D: mistral.rs first-use lead (3e; written 2026-11-24 about 08:20 UTC local, before running)

Lead: in the kernel rerun's 128-completion check, the completions that varied between launches were the first prompt with each adapter (`docs/CHANGELOG.md`, Kernel rerun B1 to B3). Question: does the first request after an adapter is first used differ from later identical requests, on the rebuilt old and new trees? GPU time at most two hours in total; correctness of output only, no timing result.
- Trees: upstream `master` at `21da642` (old) and the same plus the grouped-kernel patch `results/raw/kernel_followup/grouped_kernel_commit_600cdef.patch` (new), built with `cargo build --release -p mistralrs-cli --features "cuda flash-attn"` and the environment recorded in `followup/kernel_rerun/BUILD.md` (`CUDA_COMPUTE_CAP=89`, `CARGO_BUILD_JOBS` 8, `CUDAFORGE_THREADS` 4, `RUSTFLAGS` unset). Because the pod disk is small (about 15 GB free), the two builds run one after the other, each in an empty target directory that is deleted once the binary is copied to `/workspace/bin/`; SHA-256 and size are recorded and compared with `BUILD.md`'s values (a different checksum is reported, not hidden: rustc or host differences could change it).
- Source reading: the adapter load and first-use path in `mistralrs-core` and `mistralrs-quant/src/lora/dynamic/` (is an adapter's weight upload, slot assignment or a kernel workspace allocated lazily at first use?), recorded with file and line in `followup/mistralrs_first_use/NOTES.md`, and compared with the observation.
- Experiment (per tree, 3 server starts, alternating old and new: old, new, old, new, old, new): server as in `run_rerun.sh` (`serve -m MODEL -p 1234 --kv-cache 8GiB --max-seqs 256 --lora-max-adapters 64`, 8 adapters at scale 0.05, seeds 0 to 7). After the server is ready and nothing else has been sent: 3 base-model requests (no adapter), then for adapters 0 to 7 in order, 6 identical serial requests each (same prompt, `temperature` 0, `max_tokens` 128), then a second round of 3 identical requests per adapter. One request at a time. Output text is recorded for every request.
- Quantities: per (start, adapter): whether request 1 differs in text from requests 2 to 6, and whether requests 2 to 6 agree with each other; the same for the base-model control and for the second round (which should not differ if the effect is first use).
- Reading, fixed now: "a first-use difference" is a cell where request 1 differs from requests 2 to 6 while those five agree with each other. It is reproducible if it appears in at least 2 of 3 starts for the same adapter on the same tree. If no first-use difference appears in any cell, the lead is reported as not reproduced and the earlier variation as unexplained. Differences between old and new are reported as counts only; no claim about the kernel is made from them.
- The result goes into `docs/BUGS.md` whichever way it comes out.
