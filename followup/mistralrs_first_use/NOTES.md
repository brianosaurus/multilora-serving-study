# 3e: source notes on the adapter load and first-use path (2026-11-24; read-only; mistral.rs `master` at `21da642`)

Read on `runpod` in `/workspace/src/mistral.rs` (checked out at `21da642fdd2210c30ca4028e1eabdd28e9c602fd`). Reading only; no run. Written before the experiment of Item D, so the experiment can contradict it.

- Loading. `mistralrs-quant/src/lora/dynamic/loader.rs` plans and loads adapter weights from safetensors for each LoRA site (`plan_dynamic_lora_weights`, `load_dynamic_lora_weights`); the registry in `mistralrs-core/src/adapter/{registry,runtime,generation,selection}.rs` tracks loaded aliases and "resident generations" with a count limit and a byte budget (`runtime.rs:25-64`, errors at `:181-194`). In `mistralrs-core/src/adapter/` a search for lazy, on-demand, first-request, deferred or warm-up code found nothing: adapters named with `--lora` look like they are loaded when the server starts, not when first selected by a request. Not confirmed by a run.
- Site ids. Each LoRA site gets its id from a `OnceLock<u32>` set when the registry is finalized (`registry.rs:218-262`, `:355-372`); a request that arrives before that gets the error "LoRA layer registry has not been finalized". This is a startup step, not a per-adapter first use.
- Caches that fill during use. `execution.rs` (`LoraExecutionArena`) and `expert_cuda.rs` keep per-resource caches (routing resources, weight tables, token-slot uploads, metadata) with a counter of uploads (`cuda_stats`). They belong to the expert (mixture-of-experts) path; Qwen2.5-1.5B is a dense model, so they should not apply. The dense path calls `try_add_delta_cuda` (`cuda.rs:294`), which allocates its output and hidden buffers on every call (`cuda.rs:229`, `:261`); nothing there is keyed on "first call" in what I read, but I did not read the whole call chain from the scheduler to the kernel.
- What could still make a first request differ without being in the adapter code (hypotheses, none tested): first-use CUDA module or cuBLAS/flash-attention workspace setup changing the numerical path or the algorithm choice; the first request of an adapter meeting a different batch composition (the earlier 128-completion check ran 15 launches with one prompt per adapter in order, so "first prompt with each adapter" is also "the first requests after the server started"); non-deterministic reduction order in kernels that is more likely under a cold start. The 3e experiment separates some of these: it includes a base-model control (3 requests before any adapter request), a second round after every adapter has been used, and repeated starts.
- Limits: dense Qwen path only; CUDA path of `master` at `21da642` only; the new tree (the PR's patch) changes `dynamic_lora.cu`, `cuda.rs`, `cuda_ffi.rs` and `execution.rs` and was not read here.
