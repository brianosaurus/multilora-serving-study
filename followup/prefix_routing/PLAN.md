# 3a: routing with prefix caching on (plan, written 2026-11-24 about 06:30 UTC, local machine, before any run; runs on `runpod2` only)

Question: when requests for different adapters share a long prompt prefix and the engine's prefix cache is on, does each request still get its own adapter's output, and does the cache never serve one adapter's cached prefix to another adapter? Exploratory, separate from the pre-registered study. A pass means "no misrouting seen on these requests and this setup", not that an engine is correct.

## Method (fixed now)

- Engines: vLLM 0.34.0 with prefix caching left on (its default) and SGLang 0.5.23 with the radix cache on (no `--disable-radix-cache`). Other flags as in the A2 notes of `followup/routing/PLAN.md` (vLLM `--max-model-len 4096 --gpu-memory-utilization 0.85 --enable-lora --max-loras 16 --max-cpu-loras 64 --max-lora-rank 16`; SGLang `--max-lora-rank 16 --max-loras-per-batch 16`, seven target modules, `--mem-fraction-static 0.6` as the A2 note records). Adapters: seeds 0 to 3 at B scale 0.02 regenerated on the pod with `scripts/make_adapters.py`; their SHA-256 must equal `followup/routing/results/raw/sweep_s0.02/log_and_checksums.txt` or the run does not start. mistral.rs is not part of 3a.
- Prompts: 16 new prompts built from 2 shared prefixes of about 512 tokens each (different text), 8 distinct suffixes of 16 to 32 tokens per prefix. Every prefix is therefore shared by 8 prompts, and by all 4 adapters. Prompt text is written in `followup/prefix_routing/prompts.json` before any run and is not changed afterwards.
- References and the rule are those of `followup/routing/PLAN.md` unchanged: fp32 greedy continuations of 128 tokens for base and adapters 0 to 3 (`scripts/refs.py`, GPU, no engine running), teacher-forced log-probability distance, k = 3, noise from the bf16 stand-in's own median distance on these prompts. All four power checks must pass on the new prompts before any engine verdict; if they fail, the result is inconclusive and no engine run is interpreted.
- Probe: `engine_probe.py` as in A2 (16 prompts by 4 served adapters by 5 candidates = 320 calls per mode), in mixed mode with 16 calls in flight so all four adapters share the batch, calls shuffled with seed 7. Two passes per engine: (i) cold: server restarted, cache empty, one mixed pass; (ii) warm: a second mixed pass on the same server straight after (the cache now holds the prefixes for the adapters that used them). A serial pass is not part of 3a.
- Confirming that the cache was used and did not cross adapters (fixed thresholds, before any run):
  - vLLM: the counters `vllm:prefix_cache_hits_total` and `vllm:prefix_cache_queries_total` (or the names this version exposes; the names read are recorded) are read before and after each pass; the per-request cached-token count is read with `--enable-prompt-tokens-details` if the flag exists. SGLang: `meta_info.cached_tokens` per call (or the cache-hit counters in `/metrics`).
  - Hits confirmed if, in the warm pass, at least 50% of the shared-prefix tokens of all calls are counted as cached. If not, the run is reported as "cache not exercised" and not as a pass.
  - No cross-adapter hit: in a separate control (before the passes, on a fresh server) one call with adapter 0 on prefix A is made, then one call with adapter 1 on the same prefix A. The second call must report at most one cache block of cached tokens (16 tokens for vLLM's default block size; SGLang's page size as read from its log) inside the shared prefix. A larger count means the cache crossed adapters, which is reported as a finding whatever the routing rule says.
- Known risk, stated in advance: the A2 probe asks for logprobs of prompt tokens. vLLM may skip the prefix cache for requests that carry `prompt_logprobs`, and SGLang may only reuse the cache up to `logprob_start_len`. A 12-call smoke test decides this: if vLLM calls with `prompt_logprobs` show no cached tokens, the vLLM result is "cache not exercised by this probe" and the fallback below is used for vLLM. Fallback (declared now): for the 16 prompts and 4 adapters, greedy 32-token completions (`max_tokens` 32, temperature 0) on the warm server must equal the completions of the same server with prefix caching off (`--no-enable-prefix-caching`) in at least the fraction that two cold runs of that same server equal each other (measured first, 3 runs); a completion that equals another adapter's cold completion and not its own is a misroute.
- A misrouting (nearest candidate not the right adapter, or the fallback's misroute) is a finding: stop, reproduce with a minimal script, log it in `docs/BUGS.md`, search upstream, and tell the author before anything else.
- One engine on the GPU at a time; before each engine the GPU must be idle (no compute processes) and the quiet check of Kernel rerun Amendment 1 must pass (external CPU at most 1 core over 10 s) or the run waits; load average, GPU clocks and temperature are recorded at the start and end of each pass. A pass during which external CPU exceeds 2 cores is flagged and repeated, not used.

## Output

`followup/prefix_routing/results/raw/` (probe JSON, analysis text, counters, server logs, the setup log); a table per engine of: routed correctly (of 64) cold and warm, cache hit share, the cross-adapter control, and the power-check result.

## Limits stated in advance

Synthetic adapters at scale 0.02, one model, rank 16, four adapters, 16 prompts of about 550 tokens, two prefix groups. Two of the four adapters' cache behavior is not distinguished from the other two. The probe forces tokens instead of decoding normally, so it does not test the decode path's use of the cache. No claim about other engines, models or cache settings.

## Prompts fixed (2026-11-24 about 06:45 UTC, local machine; token counts from the Qwen2.5 tokenizer on `runpod2`, before any engine or reference run)

`prompts.json` (made by `make_prompts.py`, fixed text) has 16 prompts of 564 to 598 tokens. The shared token prefix is 579 tokens within group A (prompts 0 to 7) and 554 within group B (prompts 8 to 15); A and B share 2 tokens. This is longer than the "about 512" above; the cache thresholds are unchanged (at least 50% of the shared-prefix tokens, so at least 290 tokens of A and 277 of B must be reported cached in the warm pass).

## Gate: power checks on the new prompts (pod clock 06:28 UTC on 2026-11-24, before any engine run)

All four power checks pass under the unchanged rule (k = 3): noise (median bf16-vs-fp32 distance) 0.0204, margin threshold 0.0611. Check 1: 64 of 64 correct stand-in requests routed correctly (margin min 0.116, median 0.305); check 2: 0 of 192; check 3: 0 of 64; check 4: all 10 candidate pairs above the threshold (smallest 0.314). ## Runner and smoke criteria (2026-11-24 about 06:55 UTC, local machine, before any engine run)

Files: `prefix_probe.py` (modes mixed, smoke, control, complete), `serve.sh` (server start and stop, flags as in the A2 notes with prefix caching on; vLLM also `--enable-prompt-tokens-details`), `run_smoke_control.sh` (one fresh server per engine: 12-call smoke, then the control; no pass). The passes are run afterwards by a second script once the smoke and control results are read.
Control, as run: probe calls and plain calls (prompt only, `max_tokens` 1, no logprobs) in the order (adapter 0, prompt 0), (adapter 0, prompt 1), (adapter 1, prompt 1), (adapter 1, prompt 2); prompts 0, 1 and 2 share a 579-token prefix. Cached tokens are read per call (vLLM: `usage.prompt_tokens_details.cached_tokens`; SGLang: `meta_info.cached_tokens`); vLLM's `prefix_cache_hits` and `prefix_cache_queries` counters are saved after the control.
Reading of the control, fixed now:
- Cache works for the call type if the second call (same adapter, shared prefix) reports at least 290 cached tokens (50% of 579).
- No cross-adapter hit if the third call (other adapter, same prefix, not yet cached for that adapter) reports at most 16 cached tokens (vLLM block size; for SGLang the page size read from its log, or 1 if none is printed). More is a finding.
- If the probe-type calls report fewer than 290 cached tokens on the second call while the plain calls report at least 290, the probe bypasses the cache and the fallback in this plan is used for that engine. If neither type reports hits, the cache is not exercised and that engine's 3a result is "cache not exercised".
- If cached tokens are not reported at all (`None`), the vLLM counters decide; SGLang has no counter fallback here and would be reported as "not measured".
